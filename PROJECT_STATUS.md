Нужно реализовать **один файл интерфейса** `solution.py` с двумя частями:

- **Part B** — класс `RiskEstimator` (опциональный бонус): покадрово выдавать вероятность `P(авария начнётся в течение ближайших 5 c)`. Строго каузально.

## 2. Из чего складывается результат

```
Elimination = 0.6 · M + 0.25 · Website + 0.15 · Code

M = 0.7 · Score_A + 0.3 · Score_B      # (Score_B = 0, если в тесте нет аварий)
```

### Score_A (детекция событий)
- Per-class **macro F1** по трём порогам tIoU: **{0.3, 0.5, 0.7}**, усреднение пулом по видео.
- Классы в скору = **GT ∪ predictions** (обещают организаторы; см. evaluate.py header и README):
  - предсказали класс, но его нет в GT → F1=0 и он **добавляется в среднее** (тянет вниз);
  - класс есть в GT, но мы не предсказываем → F1=0 и он **остаётся в среднем** → от неизбежных классов не уйти, от мусорных наших — можно.
- **Стратегия:** точные классы важнее многих; в конце (День 3) — решётка `CLASSES`: удалять классы с dev-F1 < ~0.2. Классы из официального списка можно только удалять, добавлять нельзя.
- Одновариантные запреты: сегменты **одного класса не должны пересекаться** (харнесс сам дропает поздний); **разные классы могут пересекаться** (например `wrong_way` + `accident` = два события). Ограничение `end ≤ duration + 0.5`.

### Score_B (риск / антекупция; только класс `accident`)
- **H = 5 c** — горизонт (окно позитива `[s−5, s)` до старта аварии; ignored-зоны: внутри аварии и `[s−5, e]` для near_miss).
- **AP** (0.4) — chance-normalized: **константная/плоская кривая = 0**; значит риск-кривая должна быть разреженной (0 на норме, всплеск только перед аварией).
- **F1_alarm** (0.4) — порог **θ_THETA = 0.5**, runs ≥ 0.5, склейка комаров с gap < **2 c** (MERGE_GAP), матч аларма в окне `[s−10, s)`; цель — ровно один аларм на аварию.
- **mTTA** (0.2) — чем раньше аларм в окне, тем лучше; старт раньше `s−10` = FP.
- Официальный прогон вызывает `step()` на **каждом кадре** (`--risk-stride 1`); локально можно реже + повторять последний score.

### Website (0.25) и Code (0.15)

## 3. Жёсткие правила (невыполнение = 0 за видео/пакет)

- `run_submission.py` и `evaluate.py` — **харнесс и метрика организаторов, НЕ модифицировать** (Факт: этих файлов нельзя касаться редактором).
- `solution.py` — единственная точка контракта: `CLASSES`, `detect_events`, `RiskEstimator.reset(meta)` + `.step(frame, t_sec)`. Имена/сигнатуры не менять.
- `RiskEstimator.step` строго каузален: вызывается на каждом кадре по порядку, **не может открывать видео** и **не может использовать результат Part A**.
- Тайм-бюджет = **3 × длительность видео** на Part A + Part B вместе; крэш или перерасход → видео скорится как пустое.
- Оценка офлайн (без интернета): веса ≤ **5 ГБ** должны быть в репо либо скачаны скриптом `weights/download.sh` до прогона.
- **Каждое** тестовое видео обязано быть в `predictions.json`, даже с `"events": []`.
- Детерминизм: два прогона на одной машине должны давать одинаковый выход (проверка планируется в День 3; пока не фиксировали сиды формально).
- Приватность команды: **имя команды/ID/e-mail удалить из репо и истории git**. Автор коммитов — `opencode <opencode@localhost>`, remote не настроен, ничего не пушить под именем команды.

### Поведение харнесса (run_submission.py), важное для инженера
1. `load_solution` импортирует `solution.py` **по пути** из флажка `--solution` (по умолчанию `solution.py` в cwd).
2. `clean_events` дропает невалидные события и **сам** резает same-class пересечения, `end=min(end,duration)`.
3. `run_risk` вызывает `reset(meta)` + `step` на каждом N-м кадре; `meta = {video_id, fps, width, height, n_frames}`; score прижимается к [0,1].
4. Бюджет: `deadline = t0 + time_factor*duration`; проверяется в Part B каждые 100 кадров и в конце → `"events": [], "risk": []`.

## 6. Архитектура (поток данных)

```
video.mp4
  → cv2.VideoCapture (декод; каждый кадр, но обработка: каждый STRIDE-й)
  → Detector.track()  [src/detector.py]  YOLO11x (COCO car/truck/bus/motorcycle/bicycle/person) + ByteTrack
      → боксы в малом масштабе масштабируются обратно в полный 4K
  → src/rules.py  update(tracks, dets, t_sec, scene)
      TrackState на каждый id трека: label, скорость, курс, стационарность
      frame_flags() → словарь булевых флагов по 14 классам
  → src/postprocess.py  flags → сегменты [start,end] per class
      merge соседних (gap ≤ 1.0 c), отсев < 0.5 c, clean_events (union same-class, clamp end)
  → list[[start, end, label]]  (Part A)

Part B: RiskEstimator (src/risk.py) — СЕЙЧАС СТАБ, всегда возвращает 0.0.
```

Точка входа Part A = `solution.py:detect_events` → `src/pipeline.run_pipeline`.

## 8. Сейчас реализовано в rules.py (параметры по факту)

- COCO-фильтр детектора: только `car/truck/bus/motorcycle/bicycle/person` (CLASSES отсекаются остальные).
- `TrackState`: label, last_t, x, y (центр бокса), speed (px/s по dt), heading (град, atan2), stationary_at/moving_at.
- `update()`: каждая пара кадров (после stride) обновляет скорость/курс; стационарность если `speed < STILL_PX_S=2.0`. Треки без детектов удаляются сразу.
- `frame_flags()` (только эти 5 реально работают):
  - `stopped_vehicle`: везде `stationary_at` ≥ `STATIONARY_SEC=10` c.
  - `wrong_way`: `speed ≥ 2` И `_angle_dev(heading, dominant_flow_deg)` ≥ `180 − WRONG_WAY_DEV` (=100°).
  - `congestion`: ≥ `CONGESTION_MIN_VEHICLES=3` машин и ≥ `CONGESTION_FRAC=0.6` из них стоят; **гистерезис** `_congestion_hold` удерживает флаг `CONGESTION_HOLD_SEC=6` c после снятия.
  - `jaywalking`: person в `road_poly` и **не** в `crosswalk_band`.
  - `failure_to_yield`: пешеход в `crosswalk_band` И машина в `crosswalk_band` одновременно.
- Остальные 9 флагов (`solid_line_crossing, illegal_turn, illegal_u_turn, red_light, stop_line, accident, near_miss, road_obstacle, fire_smoke`) → всегда False.
- `scene.Scene.defaults_estimated(W,H)`: `dominant_flow_deg=[195.0]`; `crosswalk_band=[(1200f,850f),(3800f,1300f)]` с `f=W/3840`; `road_poly` = весь кадр кроме верха/низа (0..3840)×(200..1900).

## 9. Постпроцесс

- `segments_from_flags`: непрерывные True → [start,end]; склейка разрывов ≤ `gap_max=1.0 c`; отсев сегментов < `min_dur=0.5 c`.
- `events_from_flags`: обход 14 классов → события, сортировка по времени.
- `clean_events`: same-class union-merge (пересекающиеся сливаются в один), clamp `end ≤ duration`, сортировка.

## 10. Полуавто-разметка (label_assist.py) — как пользоваться

Назначение: ускорить ручную GT-разметку, НЕ подменять человека. Алгоритм:

1. Прогон идентичный pipeline (тот же stride/imgsz/conf/device), дополнительно копит пер-кадровые «доказательства» (id треков, курс, скорость, frac затора).
2. Из флагов строит те же события + режет **3 скриншота** на каждое (start/mid/end, 960px→1280px) с зелёными рамками детекций и подписью класса/времени.
3. Пишет `labels_draft/<video>.draft.json` (поля: event, why-текст, evidence ≤3 уникальных отсчётов, **status:"unconfirmed"**, preview-пути).
4. Черновик сжимает evidence (был блоатив 180К строк → 6 КБ; см. `_sample_evidence`).

Запуск (из `wiut_cv_scripts/wiut_cv_scripts/`):

```
python -m src.label_assist "C:\Projects\Traffic Computer Vision\video\C3905.MP4" ..\..\labels_preview ..\..\labels_draft
```

env: `TCV_STRIDE`, `TCV_IMGSZ`, `TCV_DEVICE` (дефолт `cuda:0`), `TCV_MAX_FRAMES`, `TCV_CV_THREADS`/`TCV_OMP_THREADS` (4 по умолчанию — ограничение нагрузки CPU).

Пайплайн подтверждения: человек смотрит скриншоты И/ИЛИ ролик (`video/C3905_preview.mp4`) → диктует вердикты (`да`/`нет`/уточнение [время, класс]) → подтверждённое **вручную** переносится в `my_labels.json` (главное правило: **в GT попадает только то, что подтвердил человек**).

## 11. Текущее состояние валидации на C3905 (важно, фактическое)

Прогон C3905 (полное видео, GPU, stride 3, imgsz 800, ~3 мин) → 5 кандидатов `unconfirmed`:

| Класс (кандидат) | Интервал | Вердикт человека по скриншотам (15 шт.) |
|---|---|---|
| congestion | 0.0–5.9 | ✓ «машины стоят» в начале — похоже на правду |
| failure_to_yield | 0.0–51.4 | в основном ложь; **но ~51 c машина правда не пропустила пешехода** (система пешехода не детектила) |
| failure_to_yield | 53.8–127.5 | ложь (человек: «ничего; машины стоят на пешеходе; ничего») — скорее остановка на переходе |
| jaywalking | 0.0–127.5 | начало/середина ложь; **в конце (~127 c) человек правда переходит дорогу не по переходу** |
| wrong_way | 0.1–127.5 | ложь; в конце видна **машина-разворот** → кандидат `illegal_u_turn` |

Выводы анализа для команды:
- Правило `congestion` ловит события с большой задержкой/гистерезисом; начало видео = стоящие машины.
- `crosswalk_band`/`road_poly` чересчур широкие → `jaywalking`/`failure_to_yield` ломаются почти всё видео. **Нужна нормальная геометрия из camera.md или тонкая калибровка.**
- `wrong_way` ловит джиттер треков (курс скачет) → нужен фильтр по длительности/стабильности.
- Человек смотрел статичные скриншоты — часть вердиктов сомнительна; решено смотреть ролик для точных GT.

- Локально всегда GPU (`TCV_DEVICE=cuda:0`); CPU-потоки ограничены по умолчанию.
- Правки в `rules.py`/`scene.py` сразу отражаются на финальных событиях — проверять на C3905 и сравнивать с `my_labels.json`.
- Инструмент агента **не видит изображения** в этой среде: анализ кадров только численно; визуальную валидацию делает человек.
- Детерминизм: два одинаковых прогона должны давать одинаковый результат (проверять после изменений).
- Организаторы на оценке будут в **пустой среде без интернета**: всё нужное (веса, model) должно лежать в репо или качаться `weights/download.sh`.

## 15. Глоссарий

- **tIoU** — временно́й IoU двух сегментов; пороги 0.3/0.5/0.7.
- **macro F1** — усреднение F1 по классам (сравнение каждой пары сегментов).
- **AP (Part B)** — area under precision-recall кривой риска; chance-normalized: вычитается эталон случайной кривой.
- **F1_alarm** — бинарная классификация «аларм в окне до аварии».
- **mTTA** — mean time to accident: за сколько секунд ДО аварии система подала сигнал.
- **Джвойное наказание конфузии** — FP своего класса + FN истинного класса → минус два раза.

## 16. Известные слабые места и риски

- **Нет camera.md** → геометрия грубая; может быть: неверные направления, гигантские зоны, нет стоп-линии/светофора (red_light/stop_line сейчас невозможны).
- `features.py`, `tracker_wrap.py`, `calibrate_cam.py` — заготовки, к pipeline НЕ подключены (риск «иллюзии готовности»).
- `accident`/`near_miss`/Part-B — не реализованы вообще (а Score_B = 0.3·M + потенциал).
- События, начинающиеся с t=0 (артефакты прогревшихся треков) — требуют фильтра.
- GT-разметка — незавершённая и частично по скриншотам (не по роликам) → возможные ошибки границ.
- Класс, который мы предсказываем, но которого нет в GT, получает F1=0 и **добавляется в среднее** → лишние предсказываемые классы удалять из `CLASSES`.
- Время: один видео-прогон C3905 ≈ 3 мин на GPU (см. §5) → на все 4 видео ~25–35 мин; на T4-градере быстрее.
